# External integration contracts

This file records interfaces checked against the local Payment Center and Email Center checkouts through 2026-09-29. It is a development checklist, not proof of a production connection. The SaaS app must report each integration as unconfigured until a real signed or authenticated check succeeds.

## Ownership

| Concern | Authority | SaaS responsibility |
| --- | --- | --- |
| Orders, payment evidence, Stripe events, manual payments, crypto payments | Payment Center | Create a stable intent, submit an idempotent order, verify callbacks, grant workspace entitlements |
| Referral balances, commission ledger, withdrawal approval | Payment Center | Attribute a local user, show the authoritative balance, submit a stable withdrawal intent |
| Contacts, campaign consent, unsubscribe, bounce and complaint suppression | Email Center | Capture choice and locale, enqueue ordered sync, reconcile contact state |
| Users, sessions, personal billing identities, subscription grants | SaaS | Enforce access, retain minimal external references, recover integration work through jobs and logs |

## Payment Center

- **Local referral overview, pending deployment:** Payment Center summary, ledger and withdrawal history retain legacy numeric amounts and now also return exact decimal strings. Ledger and withdrawal history accept a currency filter and offset; SaaS limits the selector to USD/USDT/USDC and never mixes rows from different currencies. The user-scoped BFF derives the user from the session, verifies the website/user/currency in Payment Center responses, strips ledger metadata and payout account details, and sends private no-store output. The multilingual dashboard shows balances, the authoritative invite/order counts, tier progress and current channel rates, a local masked invitation history, a currency-specific ledger and recent withdrawals. A local real HTTP test covers the BFF and rendered page; a mock response checks eight-decimal precision and sensitive-field removal. Commission spending and real paid-order evidence remain outstanding.
- **Local withdrawal path, pending real-provider acceptance:** Payment Center rejects a changed user, amount, currency, method or payout account on replay of one external withdrawal ID. SaaS migration `0016` stores an encrypted payout account and durable intent. The member route requires verified email ownership, a sign-in within 15 minutes, a synced referral profile, one open request at a time, and request limits. The worker checks the remote user/site binding, signs the exact request body with a dedicated secret, validates the returned receipt, and retries a timeout with the original ID. Unconfirmed outcomes eventually require manual review. A local mock HTTP test covers session scoping, replay, changed-account rejection and account masking; a browser check covers Chinese/English display and refresh recovery. The feature remains off by default. Real Payment Center balance, minimum, maintenance, payout approval and settlement behavior still need end-to-end acceptance before enabling it.
- **Local referral contract fix, pending deployment:** Payment Center's referral user upsert now keeps the first inviter binding, accepts an idempotent replay of that binding, and rejects a different inviter, self-invitation or an unknown invite code. Its API route rolls back a failed write. SaaS migrations `0014` and `0015` create stable user invitation codes in the registration transaction, an immutable local attribution mirror, and a versioned referral user outbox. An expiring HMAC cookie is issued only after authenticated attribution lookup against the website-bound `referral_read` key. A newly registered user claims it once; profile sync retries via a separate `referral_write` key. The local HTTP test covered sign-up, the invitation redirect and dashboard link, replay, a simulated network failure, retry, and the matching remote inviter; disposable users were removed. This is not acceptance of commission rates, balance/ledger UI or withdrawals.
- Use the website-specific API key for `POST /api/payment-center/orders`, catalog, and order status; never use a browser key or accept a browser-supplied amount. The SaaS pricing page mounts the Payment Center's own remote widget (`/static/js/payment-center.js`) with a short-lived embed token minted server-side by `POST /api/payment-center/embed-token`; the public `/api/payment-center/config` route exposes only the centre base URL, the site code and the methods this deployment allows, and the website API key never reaches the browser. The widget's `createOrder` callback posts to `/api/payment-center/checkout`, which creates the server-side intent and then the centre order, so the amount is always the catalogue's. Each plan card hosts one widget pinned by `productCode`; the injected script deliberately carries no `data-site`, because the centre's own auto-mount would otherwise render a second, unmanaged widget. The embedded surface is available only when the Payment Center feature switch is enabled.
- **Local website binding, verified end to end on 2026-10-04:** A separate local Payment Center website has its own site code, callback signing secret and website-scoped `create_order`/`query_order` key in the ignored SaaS `.env`. The website record's `base_url` and `callback_url` are `http://localhost:3000` (the callback allow-list is derived from `callback_url`'s hostname, and `base_url` feeds the browser-origin allow-list), and the catalog now returns two products with monthly and yearly prices. A real manual order was created through the SaaS checkout path, approved through Payment Center's own `GatewayPaymentService.review_manual` — the same service the admin 「通过」 button calls — its signed callback was delivered with HTTP 202, the SaaS Inbox worker produced one `payment_evidence` and one active `subscription_grants` row, and the signed handshake then reported `payment_pricing`, `referral` and `payment_callback` all ready. The endpoint rejects forged, stale, wrong-site and replayed challenges; its one-use challenge table is in SaaS migration `0013`. The site uses `gateway_owned_payment_evidence: true`; the referral key carries `referral_read`/`referral_write`/`withdrawal_create`, the checkout key only `create_order`/`query_order`, and `payment_ingest` remains with the payment authority. Its sole referral tier is a 0% local test tier. This is local evidence, not launch approval: real Stripe control, on-chain settlement, a human operator clicking in the real queue, real payouts, commission rules and a production site binding are still outstanding.
- **Local widget rebuild, verified live on 2026-10-04:** the pricing surface now embeds the centre's remote script the way the sibling AutoTrading application does, instead of a hand-rolled price row per currency. The four USDT catalogue prices were retired first (a USDT row is retired only when the same product and interval still has an active USD price), so the widget's interval list holds only the USD prices and a card payment is never offered a currency choice; the chain channel still settles a USD-priced plan in USDT/USDC one to one, and such an order carries the buyer's `blockchain` and settlement `currency` while `catalog_currency` stays pinned to the catalogue price. The widget's own plan picker is hidden markup and an unlocked mount silently sells the first catalogue product, which is why the page mounts one widget per plan with `productCode` locked. A fresh account paid the Starter plan with the Stripe test card `4242 4242 4242 4242` on the real hosted checkout page: the intent settled, the `payment.succeeded` notification and the `subscription.period_paid` delivery were both fulfilled inside the callback itself, and an active grant existed before the browser returned to `/dashboard` — with no `npm run payment:reconcile` run. The widget's own copy is Chinese only (the centre ships one label set; its community widget has a locale switch, the checkout widget does not), so an English page shows Chinese payment labels.
- Save a stable external order ID and idempotency key before submission. A timeout leaves the intent pending until an order query resolves it.
- The SaaS payment intent stores a stable workspace billing identity, exact catalog quote and external order key. The order client rejects a returned order with a different site, workspace, payer, product, currency or exact amount. Keep the feature switch off until the binding and grant contract pass live acceptance checks.
- The SaaS callback endpoint verifies the website HMAC over raw bytes, five-minute timestamp window and event ID before inserting a minimal Inbox record. A repeated event with the same body is acknowledged; a changed body is rejected. Unknown orders are quarantined and mismatched order IDs require manual review. The worker re-queries the website-scoped event and order before changing entitlements. The callback also fulfils the delivery it accepts: it drains that one event ID inline under a bounded time budget, so a card payment activates the subscription without a command, while a worker or `npm run payment:reconcile` stays the retry backstop for whatever it could not finish (the notification row may legitimately stay `pending` as `awaiting_period_event`).
- Treat redirects and a local `paid` flag as display signals only. First payment, renewal, refund, dispute, cancellation, and commission balance use the external authoritative record.
- **Local contract fix, pending deployment:** Payment Center now includes `amount_decimal` in catalog and order responses, and decimal amount fields in renewal/refund callbacks. Its order replay rejects a changed payer, amount, billing metadata or idempotency key. Targeted gateway and catalog tests pass.
- **Local contract fix, pending deployment:** Payment Center now stores an explicit `billing_account_id`, includes it in order responses/callbacks, and scopes open manual/blockchain order reuse and its PostgreSQL unique index to that account when supplied. Its existing Widget orders retain the legacy payer-based behavior. The local Payment Center database has applied migration `0017`; the two-workspace same-payer test passes.
- **Local contract fix, pending deployment:** Payment Center offers website-key-authorized subscription query and auto-renewal control by exact `billing_account_id` plus provider subscription ID. The old payer route remains for existing clients. The SaaS billing page now requires the personal account owner’s session and an active, settled Stripe grant tied to the original Payment Center order. Its server route verifies the returned website/account/subscription/order binding before changing renewal, avoids repeating an already applied change, and re-queries an uncertain write. A local HTTP test covers authorization, mismatch rejection and recovery with a mock Payment Center; Payment Center's account-scoped Flask contract test passes separately. A real three-project Stripe subscription test and deployment remain outstanding.
- **Local contract fix, pending deployment:** Payment Center now emits `subscription.period_paid` for account-scoped Stripe invoices with stable invoice ID, exact decimal paid amount, settlement time and a period derived only from complete subscription invoice line items. Missing or conflicting fields set `evidence_complete=false`; invoice header `period_start`/`period_end` is not used as a service period. It also exposes `GET /api/payment-center/events/<event_id>` behind the website `query_order` key. SaaS can retrieve the event by its Inbox ID without storing the full signed callback body.
- **Local Stripe period path:** The signed Inbox stores only routing identifiers and a body digest. A lease-based worker re-queries the authenticated event and order, verifies both snapshots against the stored workspace intent, and sends complete, positive-amount `subscription.period_paid` evidence into one transactional grant command. Evidence uses the invoice business key; retries do not create another grant. Payment Center queries Stripe's invoice-payment list when an invoice omits its PaymentIntent. A full `charge.refunded` or final lost dispute linked to exactly one paid invoice and the exact paid amount emits a period-specific reversal event; SaaS checks the original payment ID, amount, currency and intent before reversing only that invoice's grant. Partial or ambiguous cases, open disputes and wins enter manual review without automatic reversal. The local mock HTTP and PostgreSQL checks pass; live cross-project delivery remains unverified.
- **Local reversal recovery:** Payment Center now stores a minimal signed Stripe reversal snapshot before processing. If the paid invoice has not arrived, it retries by the same Stripe event ID through a leased queue and existing scheduler; repeated deliveries cannot alter an event's saved facts. Unmatched events eventually enter `manual_review` and can be explicitly requeued. The PostgreSQL migration and local early-refund replay test pass; an unmatched provider event still does not create a SaaS Inbox item until it is linked and emitted.
- **Local prepaid period path:** Account-scoped manual approvals and confirmed blockchain payments now include versioned `payment.succeeded` evidence with the actual payment ID, decimal amount and one calendar month or year starting at settlement. The SaaS worker re-queries the event and order, verifies the method, payer, account, quote, provider payment and calendar-duration bounds, then calls the same transactional grant service. A blockchain transfer's confirmed amount stays separate from the catalog quote and is checked against Payment Center's exact confirmed amount. Duplicate events reuse the order business key; a second overlapping paid period goes to manual review. Payment Center's scheduler revisits confirmed legacy transfers whose unified order or website event was interrupted. Mock HTTP plus PostgreSQL checks cover both methods, replay and wrong amounts. A separate real local HTTP test now proves Payment Center manual approval and simulated blockchain settlement, signed callbacks, authenticated re-query and one SaaS grant per order against isolated local databases. That test exposed and fixed an eight-hour period shift caused by writing aware UTC values to a timezone-free database column.
- **Remaining gap:** Early prepaid renewal or plan switching is currently blocked while any paid period remains; a policy for these operations, zero-amount invoices, partial-refund/dispute restoration, commission balance two-phase spending, live user-facing checkout acceptance, a live Stripe subscription-control test and production deployment are incomplete. Payment Center's current blockchain monitor settles on its existing confirmation policy, which still needs an explicit finality decision before launch. Unsupported or incomplete SaaS events enter manual review. Keep the checkout feature switch off until these contracts and recovery tests are complete.

## Email Center

- **Local ownership and password-reset links, pending production mail configuration:** The separate Resend adapter is enabled only with the transactional-mail feature, API key, sender and public app origin. Login still sends no email code; registration mails a one-time code, and the account it creates stays unusable until that code is entered. In Account settings, an unverified user can request a one-hour Better Auth verification link; the callback is pinned to the local account page. A local mock Resend HTTP test proved delivery, rejection of an external callback, the click-through `email_verified` update and a new Email Center contact outbox version. A separate one-hour password-reset link was tested through mock mail, single-use token consumption, old-session revocation, old-password rejection and new-password sign-in. The forgot-password page gives the same receipt for an unknown address. No real email was sent. The withdrawal feature is gated on ownership and recent sign-in and remains off by default.
- The application Bearer key is server only; the Widget key is public and restricted by allowed origins.
- A dedicated local `saas-framework` application and its server key now pass Email Center's authenticated integration check. Real local HTTP registration, preference, email-confirmation and opt-out events reach that application through the SaaS contact outbox. This local binding does not represent production credentials or deployment.
- The optional home-page Widget uses only that application's public key. Browser checks covered Chinese and English text, mobile display, duplicate subscription preserving one application contact, and removal when navigating to the registration page. A failed Widget script leaves the main site usable. After a request, the Widget displays a neutral receipt because an unsubscribed address is not silently reauthorized. The revised Chinese receipt was verified in a local browser with an actual accepted Widget request; the disposable contact was removed afterward. Production origin and deployment checks remain outstanding.
- `POST /api/v1/contacts/upsert` accepts stable `externalUserId`, `Idempotency-Key`, `marketingConsent`, `source`, `occurredAt`, `preferredLocale`, and `localeSource`. The first registration contact is synced with `marketingConsent=false` until email ownership is confirmed.
- Per-user events need an increasing local version and ordered delivery. When a newer event exists, an unsent older event should be superseded; a failed or timed-out send must be reconciled by contact query.
- **Native receipt recovery, pending deployment:** Email Center now exposes application-scoped `POST /api/v1/contacts/reconcile` with the original request key and contact fields in a private body. It compares the same canonical request hash as upsert and returns minimal receipt/current-binding flags from a read-only snapshot. SaaS queries this receipt before a repeated send; failed queries never authorize a resend, and remote unsubscribe or newer preferences are not overwritten. Periodic CLI/Cron/loop reconciliation shares a per-user lease with sending. Exact dead-letter recovery first queries the authority, retains the original operation and attempt history, and permits an extra send only for a confirmed missing request. See [email-reconciliation.md](email-reconciliation.md) for migration, commands and production gates.
- **Local contract fix, pending deployment:** Email Center now ignores contact events whose `occurredAt` is no later than the stored consent timestamp. A PostgreSQL integration test covers reordered events and unsubscribe. The SaaS outbox keeps only the latest unsent version, then retries with its stable idempotency key.
- **Local rebind and account flow, pending deployment:** Email Center migrations `0004` and `0005` record the external binding version and durable marketing suppression. A newer event moves one `externalUserId` to the new contact, unbinds and suppresses the old address, rejects an email already owned by a different external user, and ignores delayed old events. A marketing unsubscribe follows the identity and cannot be undone by a later profile update or Widget submission. SaaS account settings now use Better Auth to save name, locale and marketing intent. Its protected email-change endpoint requires current ownership, password proof, a sign-in within 15 minutes, same-origin requests and shared rate limits; both inboxes are confirmed before the canonical address changes. Migration `0017` revokes all old sessions atomically with that change. The local HTTP smoke uses actual confirmation links, a real Email Center unsubscribe request and the contact worker to verify suppression follows the rebind. Mail delivery is mocked; sender configuration, staging and production deployment remain unverified. Explicit re-consent after unsubscribe still needs a separate proof-bearing action. See [account-settings.md](account-settings.md).
- Email Center's current contact/campaign API is not a transactional password reset or email ownership API. These mails require a separate adapter or a separately accepted transaction-mail contract.
